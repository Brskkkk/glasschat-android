# GlassChat implementation status

Source-only status snapshot for the private repository. This work has not been built, tested, run through CI, packaged, or deployed. Jr explicitly requested that builds and packaging remain paused until the requested features and stability checks are ready. `git diff --check` is a whitespace/diff check only, not compilation or protocol verification.

| Area | Current source state |
|---|---|
| Owner and Client apps | Separate Android app modules and application IDs share the Compose messenger. Not build-verified. |
| Local data and UI | Local conversations, contacts, message search, edits/deletion, reactions, bookmarks, drafts, pin/archive/mute, themes, and profile preview are implemented as source. Local-only items remain on this device. |
| Local at-rest protection | Selected records use AES-GCM with an Android Keystore key; SQLite routing/index metadata remains visible. This is not SQLCipher or E2EE. Migration and recovery are not device-tested. |
| Supabase configuration and Auth | Both app entry points now expose HTTPS project URL and public anon-key configuration, Supabase Auth sign-up/sign-in, local sealed-session persistence/refresh, server-account lookup, invitation redemption, and device registration. Configuration and session tokens are saved in the sealed local store and sessions are bound to their configured project URL. A trusted operator must apply/review the SQL migrations and provision the first Owner account; these apps contain no service-role credential. No project URL/key was supplied, no project is configured or deployed, and no remote flow has been exercised. |
| Peer identity and Signal | The shared screen supports bilateral contact approval, fetching the consent-gated public device directory, showing Signal identity fingerprints, requiring out-of-band fingerprint entry, consuming a public prekey bundle, checking its signatures/identity, pinning the peer, and binding the session to the selected local conversation. Signal identity/private prekeys/session state are sealed locally. No on-device or interoperability validation has run. |
| Composer and inbox wiring | The Owner and Client screens now instantiate the secure runtime directly. A selected conversation only exposes encrypted send/receive controls after a verified peer session is linked to that conversation. Sending now independently Signal-encrypts a copy for every verified device of the one peer account linked to the conversation. Ratchet advances, all per-device ciphertext outbox entries, and one visible local message commit in a single SQLite transaction; relay submissions then report accepted/queued counts and preserve per-device state, including partial acceptance. If one device's encryption fails, the local batch rolls back; ambiguous multi-account mappings are refused. Sending goes through Signal encryption and a local ciphertext outbox before authenticated relay submission; receive decrypts and stores locally before acknowledging. If setup is missing, the composer can only save a clearly local-only message. There is no plaintext network fallback. Relay-accepted does not mean recipient-confirmed. After verification, both apps schedule a connected-network immediate and periodic WorkManager sync to retry ciphertext and poll inbound messages; Android may defer it. No push or message notification is implemented. |
| Relay backend source | Supabase migrations define authenticated metadata, invitation, contact-consent, public prekey, one-time-prekey consumption and ciphertext relay RPCs. Expiry is enforced on submit and expired rows are removed during fetch or via the explicit expiry RPC; no scheduled cleanup has been configured. Migrations are source only and were not applied or audited against a live project. |
| Owner foreground service | Start/pause/resume/stop lifecycle and opt-in boot-start shell exist. It does not host the relay, API, or registration authority. Android may restrict background execution; no always-on public reachability is established. |
| FCM, remaining product features | FCM/push and incoming-message notifications, groups, attachments, voice/media, recovery/backup, broader Owner administration and production reliability coverage remain unfinished. Multi-device fan-out source wiring is now present but remains unbuilt and untested; the relay still gives each device its own copy and does not confirm recipient receipt. WorkManager polling is a best-effort fallback, not push. |
| Build and delivery | No build, tests, CI, APK, packaging, or release in this work, as requested. Source was pushed to the private repository. |

## Configuration needed for live use

A trusted operator must deploy and review the included Supabase migrations, provision the first Owner account, and provide the Supabase project URL and public anon key for configuration in both apps. Auth policy may require email verification. After that, users must create/sign in to Supabase Auth, redeem an Owner invitation, register devices, approve each other, and compare the full Signal fingerprint out of band. Until this is done, the apps stay local-only; the source being wired does not establish a live service.

A ciphertext relay does not make an Owner phone publicly reachable. No free tunnel, routable carrier endpoint, paid hosting, or always-on server arrangement has been configured or selected.
