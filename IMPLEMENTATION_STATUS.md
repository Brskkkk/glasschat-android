# GlassChat implementation status

Status for the private repository. Owner and Client debug APKs have now both been built successfully and their package metadata and APK signatures verified. These are arm64-v8a-only debug previews, not production releases. The Client build completed with D8 Kotlin-metadata rewrite warnings; no runtime, device, unit, integration, interoperability, or security validation has been performed.

| Area | Current source state |
|---|---|
| Owner and Client apps | Separate Android app modules and application IDs share the Compose messenger. Both debug APKs compile/package successfully with the current API 35 toolchain. |
| Local data and UI | Local conversations, contacts, message search, edits/deletion, reactions, bookmarks, drafts, pin/archive/mute, themes, and profile preview are implemented as source. Local-only items remain on this device. |
| Local at-rest protection | Selected records use AES-GCM with an Android Keystore key; SQLite routing/index metadata remains visible. This is not SQLCipher or E2EE. Migration and recovery are not device-tested. |
| Supabase configuration and Auth | Both app entry points now expose HTTPS project URL and public anon-key configuration, Supabase Auth sign-up/sign-in, local sealed-session persistence/refresh, server-account lookup, invitation redemption, and device registration. Configuration and session tokens are saved in the sealed local store and sessions are bound to their configured project URL. A trusted operator must apply/review the SQL migrations and provision the first Owner account; these apps contain no service-role credential. No project URL/key was supplied, no project is configured or deployed, and no remote flow has been exercised. Apply migrations `0001`–`0010` in numeric order to enable the current schema, sender-visible per-device storage/expiry status, authenticated own-device prekey counting, server-authoritative Owner controls, and version-guarded server-managed group controls. |
| Peer identity and Signal | The shared screen supports bilateral contact approval, fetching the consent-gated public device directory, showing Signal identity fingerprints, requiring out-of-band fingerprint entry, consuming a public prekey bundle, checking its signatures/identity, pinning the peer, and binding the session to the selected local conversation. Signal identity/private prekeys/session state are sealed locally. On device setup, the app checks the authenticated device’s remaining one-time-prekey count and replenishes to 100 when below 20, using monotonically increasing locally sealed IDs; uncertain uploads burn IDs rather than reusing them. Migration `0006` adds the authenticated own-device count RPC. Source now stages fresh signed EC and last-resort Kyber keys after 30 days of local key age, then republishes the current pair during best-effort WorkManager sync. New IDs and private records are committed atomically; an interrupted/uncertain publication retries the same pending pair, while old private records remain to support in-flight bundles. Rotation is not time-accurate while the app is inactive and is unbuilt/unverified; no remote key cleanup or secure retirement is implemented. No on-device or interoperability validation has run. |
| Composer and inbox wiring | The Owner and Client screens now instantiate the secure runtime directly. A selected conversation only exposes encrypted send/receive controls after a verified peer session is linked to that conversation. The composer supports one inline file up to 512 KiB: its filename, MIME type and bytes are serialized inside the message plaintext, which must use the same verified Signal-encrypted send path; recipients can save the decrypted file to a user-selected location. This is a bounded single-file attachment, not a separate blob service, streaming transfer, or support for media/voice workflows; malformed attachment payloads and compatibility are not build/interoperability validated. One-to-one conversations are restricted to a single peer account; a local group can fan out an independently Signal-encrypted copy to every verified device linked to that group ID, including devices from multiple peer accounts. Ratchet advances, per-device ciphertext outbox entries, delivery mappings and one visible local message commit atomically. Direct sends report per-device acceptance, including partial acceptance; server-managed group sends submit the full active-device set through the new atomic batch RPC and report every copy accepted or queued together. If one device's encryption fails, the local batch rolls back. Sending goes through Signal encryption and a local ciphertext outbox before authenticated relay submission; receive decrypts and stores locally before acknowledging. If setup is missing, the composer can only save a clearly local-only message. There is no plaintext network fallback. The sender can refresh per-device durable-storage receipts; “stored” means saved on that recipient device, not read, and only authenticated relay metadata advances this state. The source migration retains metadata-only ack/expiry receipts; rows become eligible for purge after 30 days, but purge runs only on expiry/fetch/status RPC activity, so inactivity can extend retention. Status is exposed only to the original sender device. Migration `0006` exposes only the active authenticated device’s unconsumed prekey count. After verification, both apps schedule connected-network immediate and periodic WorkManager sync to retry ciphertext, poll inbound messages, and refresh receipts; Android may defer it. Users may opt in to generic local notifications for newly persisted messages; no sender or text is shown. Duplicate relay retries do not trigger a new alert. This is still polling, not FCM or real-time push. |
| Group messaging (source only) | Local groups remain a pairwise-encrypted shared-UUID path with no central roster. A separate server-managed text-group path adds server-created groups, expiring one-time invites, membership and roster lookup, relay-side sender/recipient membership enforcement, and current-roster preflight before sending. Each recipient device receives an independently Signal-encrypted copy; sending fails closed unless every active roster device is mutually approved, fingerprint-verified and matches the directory. Migration `0009` adds an authoritative membership version, Owner-only member removal and active-invite listing/revocation, and a version-guarded send RPC that serializes each copy with roster edits; each accepted delivery stores its roster epoch, and a removed member who rejoins cannot fetch older queued copies. A new migration `0010` adds one atomic batch RPC: it locks the group row, checks that the proposed copy set exactly matches every currently active recipient device, validates mutual consent and inserts the complete batch in one database transaction. Thus a new send is all-or-none for database acceptance; exact retries are idempotent, and previously accepted local copies remain explicitly tracked per device. A stale roster or any validation failure rejects the batch without inserting a new subset. Legacy `0009` per-copy sends can still have partial acceptance for older app versions. This remains pairwise Signal fan-out, not Sender-Key. No live or interoperability validation has run. |
| Relay backend source | Supabase migrations define authenticated metadata, invitation, contact-consent, public prekey, one-time-prekey consumption, ciphertext relay, sender-scoped delivery-status RPCs, and server-managed group membership/invites. Expiry is enforced on submit and expired payloads are removed during fetch/status/explicit expiry calls; metadata-only ack/expiry receipts become eligible for purge after 30 days; cleanup runs only during those calls, so inactivity may extend retention. No scheduled cleanup has been configured. Migrations `0006` and `0007` add own-device prekey counts and Owner-only account/device management; migration `0007` removes direct authenticated device update/delete grants. Migration `0008` adds member-scoped group discovery/roster, single-use expiring invitations, membership-checked ciphertext submission, and recipient-membership filtering on fetch. Migration `0009` adds membership-version serialization, Owner-only member removal, non-secret active-invite listing/revocation, and requires the guarded ciphertext RPC; the former unversioned group-send RPC is no longer executable by authenticated users. Migration `0010` adds atomic all-device group ciphertext batch acceptance and corrects redemption retries after a member has been removed. Source review through migration `0010` found that redeemed group invitations could misleadingly return success to the original account after its group membership had been removed; `0010` fixes that behavior. No additional concrete source-level issue was confirmed in this pass. This is not a live schema/security audit; no migrations have been applied. |
| Owner account/device administration | New source adds migration `0007` to prevent clients from directly changing/deleting device rows, and authenticated Owner RPCs/UI for listing accounts/devices, suspending/restoring client accounts, revoking devices (including deleting their published prekeys), and viewing recent metadata-only server audit events. Owner accounts cannot be suspended with this API; successful state changes are logged server-side. Migration must be reviewed/deployed before these controls can operate; no live authorization was exercised. |

## Configuration needed for live use

A trusted operator must review and deploy the included Supabase migrations `0001`–`0010` in numeric order, provision the first Owner account, and provide the Supabase project URL and public anon key for configuration in both apps. Auth policy may require email verification. After that, users must create/sign in to Supabase Auth, redeem an Owner invitation, register devices, approve each other, and compare the full Signal fingerprint out of band. Until this is done, the apps stay local-only; the source being wired does not establish a live service.

A ciphertext relay does not make an Owner phone publicly reachable. No free tunnel, routable carrier endpoint, paid hosting, or always-on server arrangement has been configured or selected. The current debug previews package only `arm64-v8a` because the large upstream Signal JNI runtime exceeded available build storage for broader ABI packaging; x86/x86_64/32-bit ARM devices are not supported by these APKs.
