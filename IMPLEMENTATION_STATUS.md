# GlassChat implementation status

Source-only status snapshot for the private repository. This work has not been built, tested, run through CI, packaged, or deployed. Jr explicitly requested that builds and packaging remain paused until the requested features and stability checks are ready. `git diff --check` is a whitespace/diff check only, not compilation or protocol verification.

|---|---|

| Local data and UI | Local conversations, contacts, message search, edits/deletion, reactions, bookmarks, drafts, pin/archive/mute, themes, and profile preview are implemented as source. Local-only items remain on this device. |
| Local at-rest protection | Selected records use AES-GCM with an Android Keystore key; SQLite routing/index metadata remains visible. This is not SQLCipher or E2EE. Migration and recovery are not device-tested. |

| Peer identity and Signal | The shared screen supports bilateral contact approval, fetching the consent-gated public device directory, showing Signal identity fingerprints, requiring out-of-band fingerprint entry, consuming a public prekey bundle, checking its signatures/identity, pinning the peer, and binding the session to the selected local conversation. Signal identity/private prekeys/session state are sealed locally. On device setup, the app checks the authenticated device’s remaining one-time-prekey count and replenishes to 100 when below 20, using monotonically increasing locally sealed IDs; uncertain uploads burn IDs rather than reusing them. Migration `0006` adds the authenticated own-device count RPC. Source now stages fresh signed EC and last-resort Kyber keys after 30 days of local key age, then republishes the current pair during best-effort WorkManager sync. New IDs and private records are committed atomically; an interrupted/uncertain publication retries the same pending pair, while old private records remain to support in-flight bundles. Rotation is not time-accurate while the app is inactive and is unbuilt/unverified; no remote key cleanup or secure retirement is implemented. No on-device or interoperability validation has run. |
| Composer and inbox wiring | The Owner and Client screens now instantiate the secure runtime directly. A selected conversation only exposes encrypted send/receive controls after a verified peer session is linked to that conversation. Sending now independently Signal-encrypts a copy for every verified device of the one peer account linked to the conversation. Ratchet advances, all per-device ciphertext outbox entries, and one visible local message commit in a single SQLite transaction; relay submissions then report accepted/queued counts and preserve per-device state, including partial acceptance. If one device's encryption fails, the local batch rolls back; ambiguous multi-account mappings are refused. Sending goes through Signal encryption and a local ciphertext outbox before authenticated relay submission; receive decrypts and stores locally before acknowledging. If setup is missing, the composer can only save a clearly local-only message. There is no plaintext network fallback. The sender can refresh per-device durable-storage receipts; “stored” means saved on that recipient device, not read, and only authenticated relay metadata advances this state. The source migration retains metadata-only ack/expiry receipts; rows become eligible for purge after 30 days, but purge runs only on expiry/fetch/status RPC activity, so inactivity can extend retention. Status is exposed only to the original sender device. Migration `0006` exposes only the active authenticated device’s unconsumed prekey count. After verification, both apps schedule connected-network immediate and periodic WorkManager sync to retry ciphertext, poll inbound messages, and refresh receipts; Android may defer it. Users may opt in to generic local notifications for newly persisted messages; no sender or text is shown. Duplicate relay retries do not trigger a new alert. This is still polling, not FCM or real-time push. |
| Relay backend source | Supabase migrations define authenticated metadata, invitation, contact-consent, public prekey, one-time-prekey consumption, ciphertext relay, and sender-scoped delivery-status RPCs. Expiry is enforced on submit and expired payloads are removed during fetch/status/explicit expiry calls; metadata-only ack/expiry receipts become eligible for purge after 30 days; cleanup runs only during those calls, so inactivity may extend retention. No scheduled cleanup has been configured. Migrations `0006` and `0007` add own-device prekey counts and Owner-only account/device management; migration `0007` removes direct authenticated device update/delete grants. Migrations are source only and were not applied or audited against a live project. |

Multi-device fan-out, sender-visible per-device storage receipts, low-water one-time-prekey replenishment, and age-based signed/Kyber key rotation are source-wired but remain unbuilt and untested; the relay gives each device its own copy and receipt means durable local storage, not that the message was read. WorkManager polling is a best-effort fallback, not push. |

## Configuration needed for live use

A trusted operator must review and deploy the included Supabase migrations `0001`–`0007` in numeric order, provision the first Owner account, and provide the Supabase project URL and public anon key for configuration in both apps. Auth policy may require email verification. After that, users must create/sign in to Supabase Auth, redeem an Owner invitation, register devices, approve each other, and compare the full Signal fingerprint out of band. Until this is done, the apps stay local-only; the source being wired does not establish a live service.

A ciphertext relay does not make an Owner phone publicly reachable. No free tunnel, routable carrier endpoint, paid hosting, or always-on server arrangement has been configured or selected.
