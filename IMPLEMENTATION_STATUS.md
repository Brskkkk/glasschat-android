# GlassChat implementation status

This is a source inspection report, not a release. The project has not been built or tested in this work, per Jr's instruction not to build/package until the requested implementation is complete and stable. Earlier repository history records a Gradle dependency-resolution failure; no APK or CI run is available as evidence.

| Area | Current state |
|---|---|
| Independent Owner and Client packages | Gradle modules and distinct application IDs are present in source; not build-verified. |
| Local conversation/contact/message UI | Local creation, message save/search, local-only message edit/delete, a local reaction, local bookmarks, autosaved conversation drafts, pin/archive/mute controls, private local contact nicknames and local removal exist in source. No remote contact lookup or transmission. |
| Local data protection | Payload JSON uses AES-GCM with an Android Keystore key. The current source binds ciphertext to record identity and routing metadata as associated data, and includes a v1-to-v2 in-place migration intended to preserve existing encrypted rows; neither behavior has been build- or migration-tested. SQLite routing/index metadata remains visible. This is not SQLCipher/full-database encryption and not E2EE. No recovery/backup UI. |
| Ciphertext delivery and Supabase client | Per-recipient-device queue storage, no-delete-on-fetch, device-matched ack and max seven-day expiry methods exist in source. `SignalMessagePipeline` prepares Signal-only envelopes and validates caller-supplied authenticated device mappings before decrypt/store. New `core-network/SupabaseRelayClient.kt` is an HTTPS-only, bounded-response REST/RPC client for Auth, account/device/prekey/contact lookup, ciphertext send/fetch/ack/expiry; it accepts URL and public anon key at construction and contains no configured project values. New `SignalSupabaseMessaging` source coordinates idempotent outbox retries and decrypt-store-before-ack receive. Supabase migration 0004 adds mutual-consent contact-device lookup. No migration is applied, no project endpoint/key/session is configured, and no live relay has been exercised. |
| Local account registry | Digest-only one-time invitation records, transactional local UUID account creation, account status changes, and per-device public-key/FCM-token records and revocation exist as local storage primitives. The Owner screen exposes local invitation creation/revocation and local account listing/suspend/restore. The invite can be copied on request; only its digest is stored locally. Registry mutations now create encrypted local audit entries in the same SQLite transaction, and the Owner screen shows recent events. This log is not server-authenticated or tamper-resistant. None of this reaches another device; no Client redemption/registration flow, authenticated remote server or server-side permission enforcement exists. |
| Owner foreground service | Start/Pause/Resume/Stop lifecycle and notification shell exist. Opt-in boot receiver starts it only when auto-start is enabled and Stop has not been explicitly selected; Android may reject/defer startup. Last service-start time is persisted. It does not host an API, account registry or relay; health monitoring, network recovery and backend restart recovery remain absent. |
| End-to-end encryption | Signal libsignal Android 0.106.2 is declared in `:core-crypto` and was selected by the owner. `SealedSignalProtocolStore.provisionInitialPublicPreKeys` now has source-only generation/persistence for an identity, 100 EC one-time prekeys, a signed EC prekey, and a signed Kyber last-resort prekey, returning public-only upload data after the private records are saved. A durable ready marker prevents silently regenerating consumed keys under reused IDs. `SignalSessionCrypto` requires an explicit expected peer identity, verifies both prekey signatures, pins the identity, and refuses encrypt/decrypt without a pinned identity and session; the store now rejects unpinned identities by default. App auth/device provisioning, public-key publication/retrieval, replenishment/rotation and identity-verification UI are still absent. A source-only `SignalSupabaseMessaging` coordinator now bridges pipeline operations to authenticated relay RPCs, and the shared Compose screen has optional send/receive callbacks; neither APK entry point supplies those callbacks, so actual app messaging remains local-only. A source-only `SignalMessagePipeline` now provides fail-closed encrypted preparation/receive methods: outbound messages require the existing pinned Signal session, encode only the Signal PREKEY/WHISPER bytes into a bounded versioned envelope, and write only that envelope to the local ciphertext queue; the returned transport payload is ciphertext-only. Inbound processing checks caller-supplied authenticated sender/recipient device mappings and expiry, decrypts only via the pinned session, and saves the result to the encrypted local message store. Local outbound ratchet advancement and ciphertext queue insertion, and inbound ratchet advancement and encrypted message persistence, now share one SQLite transaction. The coordinator and callback-based Compose integration are source-only, but no authenticated app runtime constructs them or supplies a verified peer/session. The local composer therefore remains explicitly local-only in both APKs; no plaintext send/receive fallback exists. The store encrypts identity pair, registration ID, remote identity, one-time/signed/Kyber prekeys, sessions and sender keys inside AES-GCM/Android-Keystore `SealedLocalStore` records; last-resort Kyber reuse history is retained. A source-only Supabase migration now adds contact-consent-gated bundle retrieval with atomic one-time-prekey consumption, ciphertext submit/fetch/ack and expiry RPC groundwork; it is not deployed or exercised. This remains unbuilt and untested; source inspection and `git diff --check` are not compilation or protocol tests. Local AES-GCM is at-rest protection, not E2EE. AGPL-3.0-only and unsupported third-party-use caveats are documented. |
| Authentication, network APIs and relay | The owner selected Supabase Auth/Postgres. Migrations define account/device metadata, public signed/Kyber prekeys, bilateral-consent bundle retrieval with atomic one-time-key consumption, and authenticated ciphertext submit/fetch/ack/expiry; migration 0004 adds consent-gated device-directory lookup. `SupabaseRelayClient` implements source-only HTTPS Auth/REST/RPC operations, and `SignalSupabaseMessaging` calls the transport for queued ciphertext. Configuration remains constructor/local-project input; no endpoint, public anon key, token or service-role key is checked in. No configured app session, applied migration, deployment, WebSocket, background retry or live service exists. There is no established public endpoint. |
| FCM | Not integrated. No Firebase project configuration or real token delivery path. |

Settings are encrypted at rest in the local record store. Profile data is not published or tied to authenticated identity; there is no complete live editor, animation/refraction tuning or performance adaptation. Not build-verified. |

## Reachability constraint

A ciphertext-only relay is distinct from a tunnel that makes an Owner phone reachable. The phone's carrier may block inbound connections behind CGNAT, and Android does not guarantee background process uptime. A no-cost gateway/tunnel or direct routable carrier path is not yet configured; do not describe the phone as publicly reachable. No paid hosting has been selected or authorized.
