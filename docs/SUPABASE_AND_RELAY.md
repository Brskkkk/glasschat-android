# Supabase identity metadata and encrypted relay boundary

## What is in source

`supabase/migrations/0001_glasschat_auth_metadata.sql` is schema/RLS groundwork for a Supabase project. It links a random permanent GlassChat UUID to `auth.users`, stores account/device metadata and public Signal identity/signed-prekey material, and keeps a digest rather than the one-time invite code. Invitation creation is owner-role-gated; redemption binds the currently authenticated Supabase Auth user and consumes the invite in a transaction. A trusted operator still has to bootstrap the first Owner account. These SQL routines have not been applied to a Supabase project or exercised against a live instance.

`0002_signal_one_time_prekeys.sql` and `0003_contact_keys_and_ciphertext_relay.sql` add source-only groundwork for owner-published public one-time prekeys, bilateral contact consent, contact-gated Signal bundle retrieval with atomic one-time-key consumption, and authenticated ciphertext submit/fetch/ack/expiry RPCs. Relay rows contain only bounded opaque Signal ciphertext, its SHA-256 idempotency digest, and device-routing metadata; the ack function clears the ciphertext payload after recipient acknowledgment. No plaintext conversation table/archive or private device key is stored in Supabase. The functions have not been applied or tested against a live Supabase instance; they are contracts, not a deployed service.

`core-network` now contains a source-only HTTPS/PostgREST client for Supabase password sign-in/refresh and the reviewed GlassChat account, device, public-prekey, contact-directory, bundle and ciphertext RPCs. It takes the project URL and public anon key as constructor parameters; no URL, anon key, password, access token or service-role key is checked in. Responses are bounded, token-authenticated RPCs use the current bearer token, and client code never logs message content or ciphertext. The migrations remain unapplied and untested against a live project. No project URL or anon key was supplied, so neither APK has a configured auth session or a `SignalSupabaseMessaging` instance. Do not put a service-role secret in Android source; no paid hosting or deployment has been selected.

## Relay contract (not yet running)

The local ciphertext queue still stores one opaque encrypted delivery copy per recipient device, leaves it queued on fetch, acknowledges only the matching recipient device, and enforces a seven-day maximum expiry; it is not a network relay. `SignalMessagePipeline` encrypts only through an established pinned Signal session, queues a bounded ciphertext envelope, and has a receive helper that validates caller-supplied authenticated device mappings, rejects expired copies, decrypts and stores locally. Both outbound ratchet advancement plus local queue insertion, and inbound ratchet advancement plus encrypted message insertion, now share one SQLite transaction. `SignalSupabaseMessaging` now connects this pipeline to the authenticated HTTPS RPC client in source: send encrypts and atomically queues before transport, only a matching RPC delivery ID permits relay-accepted status, and pending ciphertext retains its delivery ID for idempotent retry. Receive uses caller-supplied authenticated contact/device mappings, decrypts and stores before acknowledging. The shared composer accepts optional secure-send and receive callbacks and renders distinct local-only, local-queue, relay-accepted and received labels. Both APK entry points still supply no callbacks: there is no auth/session/contact-verification UI or configured endpoint/key to safely construct those callbacks, so their visible composer remains local-only. No plaintext fallback was added. A recipient may acknowledge only after local durable storage returns successfully.

Remaining backend/network boundaries:

- Derive sender account/device only from a verified Supabase Auth token plus an active device binding; never trust sender IDs from the request body.
- Authorize recipient and device using active account/device state and an accepted contact relationship.
- Accept only a bounded opaque Signal envelope for the selected recipient device. Do not decode, log, preview, or persist plaintext.
- Keep queued ciphertext in temporary relay storage, separate from Supabase's account database. Delete a device copy only after that device reports successful local durable storage; FCM acceptance is not delivery acknowledgment.
- The current adapter uses authenticated HTTPS REST/RPC only; no WebSocket subscription or background retry scheduler exists. Keep FCM payloads generic and non-content-bearing.
- Retain undelivered envelopes for at most seven days, then expire them and expose a delivery failure state.

The Owner foreground service remains a lifecycle/notification shell; it does not host these endpoints or provide network recovery yet. A free, reachable phone route/tunnel is not configured. Carrier NAT, power management and Android process/force-stop limits can prevent public reachability and continuous service; do not advertise the Owner phone as an always-on public server. No paid relay or VPS has been chosen. The Supabase RPC migration provides a backend route only after an operator deploys and configures a project; no such configuration or deployment is present. Authenticated peer-device mappings and a SessionCrypto session still need to be established by an app flow before the source coordinator can send/receive live messages. The coordinator, client and UI callback path were not built or tested here.
