# Supabase identity and encrypted relay

## Source wiring

Both Owner and Client app entry points use the shared `GlassChatSecureRuntime` in the Compose messenger. It accepts an HTTPS Supabase project URL and public anon key entered in the app; no project credentials are checked into source. The configuration, Supabase Auth session/refresh tokens, account/device metadata, peer mappings and Signal private state are stored through the local sealed store. A saved login is bound to its project URL and is not sent to a different configured project.

The UI source includes Supabase Auth sign-up/sign-in, current GlassChat account lookup, invitation redemption, device registration and public Signal prekey publication. On each device setup it checks that authenticated device’s remaining one-time-prekey count and replenishes to 100 when fewer than 20 remain. Replenishment advances a sealed local ID high-water mark before generating/uploading a batch, so uncertain uploads burn IDs instead of reusing possibly published keys; a later setup checks the server count and allocates fresh IDs if needed. Owner-only invitation creation requires an already provisioned active Owner account. The migration intentionally does not silently make the first registrant an Owner: a trusted project operator must provision the initial Owner. Signup may require email confirmation under Supabase policy.

The UI supports each side recording contact consent, loading the mutual-consent device directory, comparing the complete Signal identity fingerprint out of band, and explicitly entering that fingerprint before it fetches the peer bundle and establishes a pinned Signal session for a selected local conversation. A matching fingerprint is a human out-of-band check, not a claim that the contact has been independently authenticated by this app.

A selected conversation gets encrypted send/receive controls only when the runtime has a verified peer mapping for that conversation. Sending uses Signal and writes an encrypted envelope to the local outbox before trying authenticated relay RPC. A relay response must match the delivery ID before the local state is marked relay-accepted. A failure leaves the encrypted copy queued locally. Receive uses the locally stored peer mapping, decrypts and durably stores the message before sending its relay acknowledgment. The shared UI has no plaintext network fallback: with no verified session, it only saves locally and labels the message as not delivered.

Status distinction matters:

- `local_only`: saved on this device, not sent.
- `encrypted_queued_not_delivered`: Signal ciphertext is saved locally; relay acceptance is not confirmed.
- `relay_accepted_recipient_not_confirmed`: relay accepted ciphertext; recipient receipt is not confirmed.
- `received_encrypted_local`: decrypted message was saved on this device before relay acknowledgment.

Once a verified peer session is configured, the shared UI schedules a connected-network immediate sync and unique 15-minute periodic WorkManager sync in both APKs. It retries queued ciphertext and polls for inbound ciphertext, decrypting and persisting before acknowledgment. The worker also stages and publishes a fresh signed EC plus last-resort Kyber pair when its locally saved pair reaches 30 days; pending public-key publication is retried idempotently using the same sealed key IDs/material. The old private records are retained for in-flight bundles, so secure retirement/cleanup is not yet implemented. Users may opt in to generic local notifications when polling discovers newly saved messages; alerts contain no sender or message text. Android may defer or stop this work; it is not real-time push, FCM, or an always-on Owner relay. The Owner foreground service remains a local lifecycle shell, not the relay server. A send to a peer with multiple verified devices creates one separately ratcheted ciphertext envelope per device and queues all envelopes plus one visible message atomically in the local database. Direct-message relay submissions remain independent and show per-device partial acceptance. Server-managed group sends instead submit the complete device set through migration `0010`'s atomic batch RPC. Both paths retain per-device state; relay acceptance does not prove recipient receipt. These code paths are source-only and unvalidated.

## Migrations and deployment boundary

`supabase/migrations/0001_glasschat_auth_metadata.sql` defines account/device metadata and Owner-managed invitation functions. `0002_signal_one_time_prekeys.sql` adds public one-time-prekey publication. `0003_contact_keys_and_ciphertext_relay.sql` adds mutual-consent state, consent-gated Signal bundle retrieval with atomic one-time-prekey consumption, and per-device ciphertext submit/fetch/ack/expiry RPCs. `0004_contact_device_directory.sql` adds mutual-consent device discovery. `0005_sender_delivery_receipts.sql` adds sender-scoped per-device storage/expiry metadata receipts. `0006_one_time_prekey_replenishment.sql` adds an authenticated RPC that returns only the caller’s active device’s unconsumed-prekey count. `0007_owner_device_controls.sql` removes direct authenticated update/delete rights on device records and adds Owner-gated account/device listing, client suspend/restore, and device revocation RPCs. Revocation removes that device’s published one-time and signed/Kyber public prekeys; private key material remains on the device. The Owner UI only exposes these server controls when the Owner app is used, displays recent metadata-only admin events, and each server function checks the authenticated active Owner role. Successful status/revocation changes are audited server-side. `0008_server_managed_groups.sql` adds server-side group metadata, membership and one-use expiring invitations, member-only group roster/list RPCs, membership and mutual-contact checks on each group ciphertext submission, and filtering of fetched group deliveries for current members. It stores only metadata and opaque Signal ciphertext. Both apps can create/join server-managed text groups; before sending, the client verifies every active member device against the consent-gated directory and the user’s pinned fingerprint. `0009_group_safety_controls.sql` adds owner-only member removal, non-secret active-invite listing/revocation, monotonic membership-version snapshots, and a version-guarded legacy per-copy group ciphertext RPC. Each accepted copy serializes against roster edits and is stamped with the roster epoch; fetch excludes old-epoch payloads from accounts that joined or rejoined later. Retries of an already accepted identical copy are idempotent. Older clients can still leave partial fan-outs if the roster changes mid-send.

`0010_atomic_group_fanout.sql` adds a batch RPC that serializes the entire group send against membership edits, requires exact active recipient-device coverage and mutual contact consent, and inserts all new ciphertext copies in one database transaction. A new app send is all-or-none for database acceptance; a stale roster or failed validation inserts no new subset. Exact retries remain idempotent. The client groups retries by the original logical message and checks its retained per-device state; incomplete legacy fan-outs stay queued rather than being mislabeled as complete. This remains pairwise Signal fan-out, not Sender-Key.

These migrations (`0001`–`0010`) are source only. They have not been applied or exercised against a deployed database. A source-level pass over `0001`–`0009` found a redeemed-invite retry that could return apparent success after the same account's membership was later removed; `0010` rejects that stale redemption. This is not a live schema/security audit. Review the `SECURITY DEFINER` functions and policies before applying them to the owner's Supabase project. The authenticated Android client must use only the project's public anon key and user's access token; never put a service-role key in an APK.

Ciphertext relay is not a plaintext archive: it accepts bounded Signal envelope bytes plus delivery/device routing metadata, idempotently rejects a reused delivery ID with different content, and clears the payload after recipient acknowledgment. Submit limits expiry to seven days; fetch removes expired rows, and an explicit expiry RPC is available. No scheduled expiry job is configured. The 30-day receipt-retention cleanup runs only when an authenticated expiry, fetch or status RPC executes; during inactivity, expired metadata may remain longer than 30 days. Relay acknowledgments indicate recipient durable storage only when the recipient's app performs the authenticated decrypt/store-then-ack path; server acceptance alone is not delivery confirmation.
